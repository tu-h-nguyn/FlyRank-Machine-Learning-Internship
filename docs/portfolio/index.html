Search-Ranking Refresh Queue

Flagship Paper + code public

An editorial team can review about 50 pages a week out of a portfolio of 18,000. The useful question is not "which pages are bad" but which pages should be opened first — an ordering problem, not a threshold one.

Starting point
FlyRank's public internship starter repo: an anonymized 30,000-row dataset, a skeleton pipeline script and empty notebook templates. No modelling, no framing, no evaluation.
My contribution
  • Defined the decision, the label and the decision point: split one 90-day snapshot into three exact 30-day windows and predicted a >20% impressions drop in the last one.
  • Ran the leakage audit that removed every window-spanning column, including one I had been using in an earlier week.
  • Engineered the 24 decision-time features, built the rule baseline first, then the models.
  • Designed the client-grouped split, the stability check across five client holdouts, and the monitoring thresholds.
  • Wrote the 18,010-row action queue with reason codes, suggested action and confidence, plus the paper.
Approach
Leakage audit · feature engineering · rule baseline before model · logistic regression and random forest · GroupKFold(5) by client · precision@K at the team's real capacity · permutation importance · stability and error analysis
Result
Logistic regression on honest features: PR-AUC 0.718, precision@50 0.88 — against 0.668 / 0.74 for the rule baseline and 0.617 for random ordering, on a 0.62 base rate. Stable across five client holdouts (PR-AUC 0.668 ± 0.026). The grouped split scored 0.042 lower than a naive random-row split — evidence that the split design, not the model, was doing the honest work. An earlier rule of mine scored only 12 of 18,010 pages above zero (ROC-AUC 0.500) and is reported as a failure in the paper.

02

Sharp CFL Analysis — FEM for the Wave Equation

Report + code public

Every course quotes Δt ≤ h/c as the stability limit for explicit time-stepping on the wave equation. With a consistent mass matrix that bound is wrong, and a scheme built on it diverges — quietly, because the unstable mode is the one your initial data barely excites.

My contribution
  • Two-person coursework report; everything below — the verification, the fix, the pipeline — is mine.
  • Built the reproduction harness that recomputes all four tables from source and fails on any mismatch against the published PDF. It runs in CI on every push.
  • Found and fixed a real reproducibility gap: the published growth() listing could not generate the report's own Table 3.
  • Wrote the figure pipeline that renders the report's figures and the web page's from one set of computed arrays, so the two cannot drift.
Approach
Closed-form spectrum of the stiffness/mass pair (S, T) · necessary and sufficient stability condition · Ritz projection for the convergence proof · Thomas algorithm, O(N) per step · four numerical experiments · machine-checked tables
Result
Two distinct CFL constants where the literature usually states one: Δt < h/(c√3) for the consistent mass matrix and Δt < h/c for the lumped one. The measured threshold matches the analytic θ* to four significant figures, and convergence lands on 2.00 in L² and 1.00 in H¹ across six refinements. All four tables reproduce digit-for-digit — after the harness caught that the shipped code was missing the 1e-8 mode seeding the report describes.
Python · NumPy · Matplotlib · LaTeX (XeLaTeX) · GitHub Actions

03

Finite-Volume Solver for the 1D Euler Equations

Package + tests public

The Euler equations grow shocks, contacts and rarefaction fans out of smooth initial data. A scheme that looks convincing on a smooth problem can be quietly wrong at a discontinuity — so the question is not whether the plot looks right, but what it is being measured against.

Approach
An exact Riemann solver as ground truth, then everything measured against it: four numerical fluxes (Lax–Friedrichs, Rusanov, HLL, HLLC) · MUSCL piecewise-linear reconstruction with four TVD limiters and a positivity safeguard · three SSP time integrators · a CLI and a library API
Result
On Sod's shock tube (N = 200, CFL 0.4, t = 0.2) the L¹ error in density falls from 3.274e−02 for Lax–Friedrichs to 4.446e−03 for MUSCL–minmod — 7.4× smaller on the same grid. A grid-convergence study confirms the schemes reach their design order rather than merely looking smooth. 133 tests, 98% coverage, mypy clean, CI on every push, MIT.
My role
The repository is mine — the package layout, the exact Riemann solver used as ground truth, the test suite, the CI, and the one-command path from source to every table and figure it publishes. The report behind it is four-person coursework (Nông Thanh Toàn, Nguyễn Hoàng Tú, Lê Minh Tuấn Kiệt, Đặng Kim Bảng) — Chuyên đề giải tích số, VNU-HCM University of Science, 2025.

04

Linear Multistep Methods — Dahlquist, Derived Not Quoted

Library + tests public

Courses state the equivalence theorem — a linear multistep method converges if and only if it is consistent and zero-stable — and the BDF barrier at k ≤ 6, as facts to memorise. Both are checkable by machine, and checking them is more instructive than quoting them.

Approach
A library that hard-codes no conclusions. Feed it the coefficients (αj, βj) and it derives the order, the error constant, the roots of the characteristic polynomial, zero-stability and the absolute-stability region — so the textbook claims become test assertions rather than prose.
Result
Measured order agrees with theory to within 0.12 across eight zero-stable methods. BDF loses zero-stability exactly at k = 7 (max|zi| = 1.0222) — the k ≤ 6 boundary falls out of the polynomial roots instead of being assumed. And the point of the whole theorem, made concrete: a consistent order-3 method that is not zero-stable reaches error 10³⁷ by t = 6. 86 tests, CI, MIT.
My role
The library and its test suite are mine — the design decision that nothing is hard-coded, so each textbook claim becomes an assertion the build has to satisfy, is the whole point of the repository and it is my work. The report is three-person coursework (L. T. Nhân, D. T. H. Yến, N. H. Tú); its 63 pages and the 50-page slide deck are in the repo.
Python · NumPy · pytest · ruff · GitHub Actions · LaTeX

06

Inexact and Accelerated Proximal Point Algorithms

Report + code public

The accelerated proximal point method assumes each inner subproblem is solved exactly. In practice it never is — so the question is how much inexactness the O(1/k²) rate survives.

Approach
A synthetic LASSO (n = 80, m = 30, sparsity 8) run through the inexact accelerated method against a classical proximal-point baseline, under four inner-loop schedules — constant, log, √k, and exact — each traced against the O(1/k) and O(1/k²) reference rates, plus a direct numerical check of the convergence bound proved in the report.
Result
The experiments show which inner-accuracy schedules preserve the accelerated rate and which decay to the unaccelerated one — the theorem's hypothesis made visible rather than assumed.
My role
The repository is mine — the MATLAB and Python experiments, the build that keeps report, slides and presentation script generated from one set of source files rather than three drifting copies, and the verification that turned the report's convergence bound into something CI checks: 0 violations across 121 outer steps for all five inner-accuracy schedules, plus the theorem's own hypothesis, which the closed form satisfies exactly. 90 checks in total, mutation-tested — 10 deliberately planted bugs, all 10 caught. The written work is group coursework (Nhóm 10), optimisation topic.

04 Method

How I approach an ML problem

This is the order I actually work in. It is also the order in which the capstone above was built, and why its honest score is lower than its leaky one.

01Define the decision first. What does someone do differently because of the output? That fixes the label, the grain and the evaluation metric — before any modelling.
02Audit the data for leakage. Every feature gets checked against the decision point. Anything that spans the outcome window is dropped, however predictive it looks.
03Build a transparent baseline. A rule or a simple model, scored the same way. If the model cannot beat it, the model is not the answer.
04Experiment systematically. One change at a time, a fixed seed, and the same split for every candidate so the comparison means something.
05Compare, then attack the result. Check stability across holdouts, inspect what the model leans on, and look for the split design that would make the number collapse.
06Write down what did not work. The failures and limitations go in the report next to the results — they are what makes the results usable.
